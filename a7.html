A7: Health Aid Proximity Webcam — QT Py SAMD21 + VL53L4CD + BetterTouchTool

HCDE • Adafruit QT Py SAMD21 • VL53L4CD Time-of-Flight Sensor • CircuitPython • BetterTouchTool • HUD Overlay System

Overview

This project implements a health-aid proximity webcam that monitors how close a user is sitting to their laptop screen using a VL53L4CD time-of-flight sensor. The system runs on an Adafruit QT Py SAMD21 using CircuitPython, streaming distance readings to macOS via USB.

A background AppleScript in BetterTouchTool (BTT) interprets the incoming serial data and triggers color-coded HUD overlays:

  • SAFE (green overlay) — user is at a healthy viewing distance
  • MID (yellow overlay) — user is approaching the screen
  • CLOSE (red overlay) — user is too close
This system provides real-time, continuous visual feedback that encourages healthy posture and safe screen distance habits.

Firmware & Software Integration

The proximity detection system consists of three coordinated software components: (1) CircuitPython firmware running on the QT Py SAMD21, (2) a Python serial bridge that listens for distance updates and fires BetterTouchTool named triggers, and (3) a BetterTouchTool keyboard shortcut that toggles the Python bridge on/off.

1. CircuitPython Firmware (QT Py M0)

The QT Py reads distance values from the VL53L4CD ToF sensor and prints one of three textual states (SAFE, MID, CLOSE) to the serial port. The BTT Python bridge listens to these messages in real time. 


      # --- code.py (runs on QT Py SAMD21) ---
      import time
      import board
      import adafruit_vl53l4cd
      
      # Initialize I2C bus and VL53L4CD sensor
      i2c = board.I2C()
      vl53 = adafruit_vl53l4cd.VL53L4CD(i2c)
      vl53.start_ranging()
      
      while True:
          if vl53.data_ready:
              d = vl53.distance        # distance in millimeters
              vl53.clear_interrupt()
      
              # Distance thresholds
              if d < 30:
                  print("CLOSE")
              elif d < 50:
                  print("MID")
              else:
                  print("SAFE")
      
          time.sleep(0.2)

2. Python Serial Bridge (Triggers BTT Named Triggers)

This script continuously reads the QT Py’s serial output. When the distance category changes, it fires a corresponding BetterTouchTool Named Trigger. These triggers activate the color-coded HUD overlays. 


      # --- btt_bridge.py ---
      import serial
      import os
      
      # Open QT Py serial port
      ser = serial.Serial('/dev/cu.usbmodem1101', 115200)
      last_value = None
      
      # Helper function: fires a BTT named trigger using AppleScript
      def fire_trigger(trigger_name):
          os.system(
              f"""osascript -e 'tell application "BetterTouchTool" to trigger_named "{trigger_name}"'"""
          )
      
      while True:
          line = ser.readline().decode().strip()
      
          if line in ["SAFE", "MID", "CLOSE"] and line != last_value:
              trigger_map = {
                  "SAFE": "distanceSafe",
                  "MID": "distanceMid",
                  "CLOSE": "distanceClose"
              }
      
              fire_trigger(trigger_map[line])
              print("Triggered:", trigger_map[line])
              last_value = line

3. BetterTouchTool Keyboard Shortcut (Start/Stop Python Bridge)

To give the system an easy on/off switch, a BTT keyboard shortcut (Command + Shift + F) runs this shell script. If the serial bridge is running, it stops it. If it is not running, it launches a fresh background instance. 


      # --- BTT Toggle Script (Shell Script / Task Action) ---
      if pgrep -f btt_bridge.py > /dev/null; then
          pkill -f btt_bridge.py
      else
          python3 ~/Desktop/btt_bridge.py &
      fi

This prevents duplicate serial listeners, ensures reliability, and allows the user to enable/disable proximity monitoring instantly from anywhere in macOS.

Distance Threshold Calculations

Placeholder values were chosen based on common ergonomic guidelines: 


        SAFE:  > 50mm   (Healthy viewing distance)
        MID:   30 - 50mm
        CLOSE: < 30 mm   (Too close, increased eye strain risk)

The VL53L4CD has a precision of ±1 mm and ranges up to ~1200 mm indoors, making it suitable for detecting real-time user movement. The polling frequency (20 Hz) is fast enough for smooth overlay updates without noticeable lag.

3D-Printed Enclosure Design

To house the QT Py M0 and VL53L4CD sensor, I designed a compact two-piece 3D-printed shell tailored around the exact dimensions of the components. Because this device is intended to sit directly on top of a laptop screen, the enclosure needed to be as small, unobtrusive, and visually condensed as possible while still protecting the electronics.

The top module holds the VL53L4CD time-of-flight sensor with a forward-facing window to ensure clean infrared readings. The lower module houses the QT Py microcontroller, with an internal cable channel that routes the STEMMA QT cable safely between boards.

The design is fully modular: both halves slide apart without screws, allowing the user to remove or reinsert the electronics at any time. This is especially helpful for:

  • Resetting or reflashing the microcontroller
  • Inspecting or replacing the sensor
  • Experimenting with alternative layouts or upgrades
The shell’s exterior geometry is intentionally minimalist, so it blends into the bezel of a laptop without blocking the built-in webcam or distracting the user. The bottom surface aligns naturally with the top edge of the display, making the device feel like a native accessory rather than an attached tool.

Reflection

I used the QT Py SAMD21 for the purposes of this project because it is significantly smaller and allows the entire proximity-sensing system to fit into a compact, unobtrusive 3D-printed case. It also has a built-in STEMMA QT connector that works directly with the VL53L4CD ToF sensor using I²C, without needing jumper wires. Because the QT Py runs at 3.3V logic (matching the sensor) and supports the quick-iteration CircuitPython workflow, it was a more practical and efficient choice for the polished, product-like final prototype that I was aiming to create. Although my experience differs between programming firmware in Python vs. C++ (as we have done in this class), the circumstances listed above led me to believe that it was a more fitting option for the product that I had aimed to create. From my experience, C++ is a powerful language for lower-level, embedded programming, perfect for the projects we had been working on up until this point. The differentiating factor for using python was the fact that I could edit code and have immediate feedback from the harware without reflashing firmware, allowing me to quickly and efficienctly debug. Since this is a product which I would like to continue optimizing for personal (and hopefully commercial use in the future), I wanted to create it in a way that would allow for rapid iteration and prototyping. Making edits to the code and seeing immediate feedback leads me to believe that it is the optimal direction for where I want to take this project.
